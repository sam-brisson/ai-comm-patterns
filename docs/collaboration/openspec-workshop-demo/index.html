OpenSpec Workshop Demo

This page outlines a demonstration approach that shows OpenSpec in action on a real project. The goal is to make the workflow tangible: your audience sees documentation emerge from workshop conversations at the same time the solution is built.

The Challenge with Abstract Demos​

When explaining OpenSpec, we face a bootstrapping problem:

  • Self-referential examples are confusing — showing OpenSpec building OpenSpec requires understanding the system first
  • The knowledge site is too complex — it has history, context, and infrastructure your audience doesn't share
  • Screenshots don't convey the workflow — people need to see the progression from conversation to artifacts to working code

We need a separate, simple project where the audience can follow the entire journey from a workshop conversation to shipped features with documentation.

The Demonstration Strategy​

The Setup: A Simple Demo Repository​

Create a minimal project repository (separate from the knowledge site) with:

  • A simple, understandable purpose (e.g., a CLI tool, a small web app, a utility library)
  • OpenSpec infrastructure already wired up (GitHub Actions, Claude Code skills, the openspec/changes/ folder structure)
  • An initial working state that can be enhanced in visible ways

Example project ideas:

  • A team standup CLI that posts to Slack
  • A simple expense tracker web app
  • A markdown documentation generator
  • A meeting notes summarizer

The key is that enhancements are obvious and demonstrable — your audience can see what changed.

The Workshop Format​

Run a live (or recorded) workshop session where the team discusses what to build. The transcript feeds into the OpenSpec workflow, and both documentation and code emerge together:

Key insight: Code is added to the demo repository during the Applied stage, while documentation artifacts accumulate throughout the workflow. By the time you reach Archive, both the working feature and its complete documentation exist together.

Walking Through the Workflow​

The demo walks through each stage using the existing workflow board from OpenSpec Changes, but pointing at the demo repository:

Stage 1: Exploring​

Show the workshop transcript being processed. The audience sees:

  • Raw conversation goes in
  • Structured exploration notes come out
  • Key decisions and open questions are identified
  • The change appears in the "Exploring" column on the board

Stage 2: Proposed​

Run /opsx:propose and show artifact generation:

  • proposal.md emerges — the "why" captured from workshop discussion
  • design.md emerges — technical approach synthesized from team input
  • tasks.md emerges — implementation breakdown ready for execution

The audience sees the change move to "Proposed" on the board. A PR is created for review.

Stage 3: Applied​

Run /opsx:apply and show implementation:

  • Claude reads the design and tasks
  • Code is written with full codebase context
  • Any "gotchas" or deviations from the plan are captured
  • The feature actually works — demonstrate it

The change moves to "Applied" on the board.

Stage 4: Archived​

Run /opsx:archive and show knowledge capture:

  • Final learnings documented
  • "Planned vs. actual" comparison shows what changed and why
  • The change moves to "Archived" — now part of institutional memory

The Payoff: Documentation That Wrote Itself​

At the end of the demo, show the audience two things side by side:

What the team didWhat now exists
Had a workshop conversationStructured proposal explaining WHY
Made some decisions out loudDesign document capturing HOW
Discussed implementation detailsTask breakdown tracking progress
Built and shipped the featureWorking code + deviation notes
Finished the workArchived knowledge for future reference

The documentation didn't require a separate writing step. It emerged from the workflow.

Connecting to the Knowledge Site​

The demo repository can feed into the knowledge site in two ways:

Option A: Embedded Demo​

The demo project's workflow board is embedded or linked from this knowledge site page. Visitors see:

  • The demo repository (separate, simple, followable)
  • Its OpenSpec changes progressing through stages
  • Links to the actual artifacts and code

Option B: Mirrored Examples​

Key examples from the demo repository are copied/published to the knowledge site's archive. Visitors can:

  • Read the workshop transcript that started it
  • See the generated artifacts
  • View the shipped code
  • Understand the full journey

Running Your Own Demo​

To create a similar demonstration for your team or audience:

1. Set Up the Demo Repository​

# Create a new repo with OpenSpec infrastructure
# (We'll provide a template repository)

gh repo create my-openspec-demo --template openspec/demo-template

2. Prepare a Workshop Scenario​

Choose an enhancement that:

  • Is easy to understand (no domain expertise required)
  • Has visible results (UI change, new CLI command, observable behavior)
  • Involves some decisions (format choices, placement, scope)

3. Run the Workshop​

Record or transcribe a 15-30 minute team discussion about the enhancement. This is the raw material.

4. Execute the Workflow​

Walk through /opsx:explore → /opsx:propose → /opsx:apply → /opsx:archive, showing each stage.

5. Show the Results​

  • The feature works
  • The documentation exists
  • The knowledge is archived

What This Demonstrates​

The demo makes three things concrete:

  1. Documentation emerges from development — not written after the fact
  2. Team conversations become institutional memory — the "why" isn't lost
  3. The workflow is practical — it works on real projects, not just the knowledge site itself
